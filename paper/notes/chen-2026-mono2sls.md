# Chen, Su, Su, Yu, Zheng — "Mono2Sls: Automated Monolith-to-Serverless Migration via Multi-Stage Pipeline with Static Analysis", arXiv:2604.24550, 2026

**bib key:** `chen2026mono2sls` — **THE closest prior work.** Almost the same shape as
ALMS. Our positioning must differentiate on hosting/resources, not on being "first".

---

## Problem / claim
Migrating monolithic web backends to serverless (AWS SAM) is still mostly manual: it
needs coordinated changes to program structure, source code, IaC config, and
cloud-specific design, kept consistent across many artifacts. Single-prompt LLM
generation cannot maintain that long-range consistency; cloud APIs are large
(SAM config space > 800 resource types) and evolve fast, so code LLMs misuse
infrequent APIs.

## Method
Static-analysis-driven **multi-stage pipeline**. Lightweight static analysis first
emits `analysis_report.json` (authoritative input) + `symbol_table.json` (for a code
RAG index):
- **HTTP entry points** via AST (Python: `@app.route/@app.get`, Flask blueprints;
  JS/TS: regex on Express).
- **File tags** `{AWS_SDK, DynamoDB, Auth, FileUpload}` via keyword matching.
- **Cross-file call graph with async semantics**: two-pass (import map, then call
  edges); each edge records `return_value_used` and `is_awaited`; aggregated per
  entry point → reduces Architect search from O(n²) to O(1) per endpoint.
- **DynamoDB schema locator**: priority heuristic (init scripts ≻ db/models config ≻
  business logic), top-3 candidate files recorded.

Then **four sequential tool-using LLM agents**, communicating only through files (no
direct inter-agent messaging), each with a role-specific toolset + a **least-exposure
slice of a curated domain KB** (4 docs from AWS SAM/Lambda guides):
1. **Architect** — consumes `analysis_report.json`, emits `blueprint.json` (the single
   source of truth): Lambda boundaries (one per business endpoint), inter-Lambda
   comm pattern (sync invoke / SQS / EventBridge, chosen from the async flags +
   autonomous deeper source reading), shared infra, auth strategy.
2. **CodeDeveloper** — one Lambda handler per blueprint entry. Framework adaptation
   (Flask/Express → `lambda_handler(event, context)`), identity-model adaptation
   (integer `user_id` → Cognito Sub UUID; Users table removed), state elimination
   (globals → env vars), shared Lambda Layer when a util is reused ≥ 3×.
3. **SAMEngineer** — `template.yaml` in 3 topologically-layered sub-tasks (stateful
   resources first for `!Ref`/`!GetAtt` anchors), with a `cfn-lint` validate→fix loop.
4. **ConsistencyValidator** — **11 cross-artifact checks in 5 phases** (Structural,
   Code↔Template alignment, Blueprint matching, Async resources, Runtime compliance);
   batch-fixes mismatches, re-validates, anti-loop safeguards.

Tools: ReadFile/WriteFile (with AST/JSON/YAML syntax validation), FileList,
**CodeRAGTool** (offline RAG index over source chunks, CodeBERT embeddings +
LlamaIndex, retriever-only — no LLM synthesis), SAMValidateTool (wraps `cfn-lint`).

## Evaluation setup
- **Benchmark:** 6 web apps **reverse-engineered** from `aws-samples` reference
  serverless implementations (screened top 270 → 12 → 6). Each turned into an
  equivalent Flask/Express monolith (Cognito → JWT middleware, SQS/EventBridge →
  sync but leaving detectable async signals, frontend removed). Sizes 601–3,623 LoC,
  **6–26 observable business endpoints, 76 total**, Python + JavaScript.
- **RQs:** RQ1 Deployability, RQ2 Functional Correctness, RQ3 **Ablation** of
  static-analysis-driven architecture planning, RQ4 Cloud-Native Design Adoption.
- **Baselines:** Commercial — **Cursor** (Agent mode, Claude Sonnet 4.5 Thinking) and
  **Claude Code** (CLI, Claude Sonnet 4.6), each given full source + a task prompt,
  no static analysis, **expert-assisted fixes allowed**. **LLM-Baseline** — one
  generalist agent, same inputs as Mono2Sls, 7 tasks collapsed to 2, no
  ConsistencyValidator, high-level prompts; two backbones **DeepSeek-V3.2** and
  **Claude Sonnet 4.6**. Ablation — remove static analyzer + Architect.
- **Metrics:** Validation Pass Rate (VPR, `sam validate` + `cfn-lint`), Deployment
  Success Rate (DSR, real `sam deploy` to live AWS), **API Coverage F1** (generated
  vs 76 reference endpoints), **End-to-End Pass Rate** (E2EPR, micro/macro over a
  145-test suite generated by GPT-5.4 + expert review; Core+Robustness = 121 tests
  primary). **pass@1, single run**, default temperature.
- **Environment:** pipeline runs locally on **Windows**; backbones are **hosted
  commercial/large models**; generated apps deployed to real AWS.

## Headline numbers
- Mono2Sls: **100% VPR and 100% DSR** (6/6) for both backbones, **no manual fixes**.
- **API Coverage F1 0.987** (Sonnet) / **1.000** (DeepSeek) vs commercial 0.884–0.889,
  LLM-Baseline 0.974–0.994.
- **End-to-end correctness (micro-E2EPR): M2S-Sonnet 66.1%** vs Claude Code 61.2%,
  Cursor 53.7% (and commercial baselines got expert-assisted deploy fixes; Mono2Sls
  evaluated on raw output). LLM-Baseline ~34.4–34.5% (only over the 3/6 apps each
  could deploy).
- **Ablation (RQ3):** removing static analysis + Architect drops DSR 6/6 → 3/6,
  F1 0.987 → 0.915, and micro-E2EPR on the comparable deployable subset
  **61.7% → 38.3% (a 23.4 pp gap)**. "Pipeline design matters more than the choice of
  backbone model."
- **RQ4:** AWS-native auth (Cognito) in all 6 apps; commercial baselines keep the
  monolith's JWT design and emit 19 redundant `/register`,`/login`,`/me` endpoints.
  Reconstructs event-driven async chains where baselines stay synchronous.
- **Cost/time:** M2S-Sonnet took **58–106 min per app** (601–3,623 LoC), dominated by
  the CodeDeveloper's iterative transformation. Frames migration as "weeks of manual
  refactoring → hours of automated processing".

## Stated limitations / threats
Benchmark = 6 reverse-engineered apps, no heavy-ORM / multi-DB legacy enterprise
systems. AWS-SAM-specific (ideas claimed transferable but need platform KBs). Async
E2E only 67% pass. **LLM inference non-deterministic; pass@1 does not measure
run-to-run variance; multi-run statistical testing left to future work.**

## How ALMS relates (the contrast to write)

| Dimension | Mono2Sls | ALMS |
|---|---|---|
| LLM hosting | **hosted commercial / large** (Cursor, Claude Code, DeepSeek-V3.2, Claude Sonnet 4.6) | **local Ollama, `qwen2.5-coder:7b`** |
| Hardware | dev laptop for orchestration, but relies on cloud LLM APIs | **single CPU laptop, ~16 GB, no GPU, offline** |
| Cost | per-token API cost; 58–106 min/app of paid inference | **$0 API cost** |
| Target | AWS SAM serverless (vendor-locked) | **portable containerised FastAPI + docker-compose** |
| Boundary selection | LLM **Architect** agent from a static dependency map | **deterministic Louvain community detection** on the call graph (seed-fixed), LLM only refines |
| Validation | 11-point cross-artifact ConsistencyValidator + `cfn-lint` | `py_compile` gate + bounded regeneration retry loop + Pydantic contracts |
| Human-in-loop | none | **3 approval gates** with reject→iterate |
| Reproducibility | pass@1, non-deterministic hosted models, variance unmeasured (their own stated threat) | fixed Louvain seed; local model; artifact + one-command `--demo`; **directly addresses their open threat** |
| Eval scale | 6 reverse-engineered apps, live AWS deploy, F1/E2EPR | 1 case study (`sample_monolith`); partner may extend — acknowledge as the main limitation |

**Shared design DNA to acknowledge, not hide:** static analysis anchoring LLM
reasoning; multi-agent decomposition with explicit typed artifacts between stages;
curated domain KB with per-agent scoping; a validate→fix loop. ALMS's novelty claim
is **not** the pipeline pattern — it is demonstrating that the pattern works with a
7B local model on commodity hardware, and pairing it with deterministic
graph-based boundary selection + HITL governance.

## Citable sentences
- **Intro** (motivation): "existing assistants are not designed to maintain the
  long-range consistency that serverless migration requires" — decisions about
  boundaries, APIs, handlers, IaC "must remain aligned across multiple generated
  artifacts". Use to motivate the deterministic-scaffold split.
- **Intro / Related work**: Mono2Sls and similar "reason about logical boundaries but
  stop short of producing deployable infrastructure" — position ALMS as also
  producing deployable output, but portable + local.
- **Related work**: their ablation result — static-analysis-driven planning
  contributes **23.4 pp** to end-to-end correctness; "pipeline design appears to
  matter more than the choice of backbone model." **This is the citation that
  licenses ALMS's whole bet**: if pipeline structure > model strength, a small local
  model inside a good pipeline is viable.
- **Evaluation** (method framing): adopt their metric vocabulary — Validation Pass
  Rate, Deployment/Build Success, API Coverage, end-to-end pass rate — scaled down
  to a single case study.
- **Discussion / Threats**: cite their admitted limitation ("LLM inference is
  non-deterministic ... pass@1 does not measure run-to-run variance") as a gap ALMS
  partially closes with a fixed clustering seed and a reproducible local artifact.
